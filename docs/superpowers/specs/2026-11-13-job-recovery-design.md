# 任务持久化与重启恢复设计

**日期：** 2026-11-13
**状态：** 按已批准的第五阶段顺序实施

## 目标

HTTP 服务重启后能够查询历史任务、恢复中断任务并复用已有转换结果，同时保持用户隔离、并发上限和现有接口兼容。

## 持久化内容

每个任务目录继续保存 `job.json`，并新增：

- `input.json`：用户、完整生成选项、validate 和原始图片路径。
- `conversion.json`：成功转换的完整 Node API 结果，用于缓存恢复。
- 现有源码、原图、截图、差异图和质量历史产物保持不变。

## 恢复规则

- `succeeded`、`failed`：原状态载入，可查询和下载已有产物。
- `queued`、`running`：统一恢复为 `queued`；优先使用任务目录的 `source.png`，否则使用仍存在的原始上传文件。恢复任务进入同一有界队列。
- 成功任务存在 `input.json`、`source.png` 和 `conversion.json` 时，按当前模型/校验配置重新计算缓存键并恢复缓存；配置变化自然产生不同键。
- 旧版本缺少新增文件时仍恢复任务状态，仅跳过缓存。
- `createServerApp()` 在接收请求前等待恢复。直接构造 `JobService` 的现有测试和调用方可显式调用 `restore()`。

## 安全与限制

- 只读取配置 `dataDir/jobs` 下的任务目录，不执行文件内容。
- 输入恢复后仍通过 `userId` 校验所有权。
- 缓存恢复不调用模型；缓存命中任务生成独立产物并标记 `cacheHit: true`。
- 本阶段仍为单进程队列，不实现多实例争抢、分布式锁或数据库迁移。

## 验证

- 重启后 completed/failed 状态和产物可读取。
- running/queued 任务被重新执行并完成。
- 相同图片与选项在重启后命中缓存，转换器调用次数不增加。
- 用户隔离、全部既有测试、类型检查和构建通过。
